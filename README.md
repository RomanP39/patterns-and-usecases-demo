### 📝 Описание процесса работы почтового протокола
Диаграмма последовательности (Sequence Diagram) пошагово моделирует сквозной процесс отправки электронного сообщения:
1. **Инициация:** Пользователь (Отправитель) создает интерфейсное событие «Написать сообщение» через клиентское приложение (`ящик_отправителя`).
2. **Маршрутизация:** Локальный клиент передает сформированный пакет данных на исходный почтовый `SMTP_сервер`.
3. **Резолвинг:** `SMTP_сервер` обращается к системе доменных имен (`DNS`) для поиска MX-записей и определения точного IP-адреса целевого почтового сервера получателя.
4. **Безопасность:** Между серверами устанавливается защищенное соединение с использованием шифрования TLS.
5. **Транспортировка и Доставка:** Письмо перемещается на целевой `Google_сервер`, который осуществляет его раскладку в физическое хранилище (`ящик_получателя`).
6. **Оповещение:** Конечный Получатель мгновенно получает push-уведомление о новом письме и при открытии приложения скачивает визуальное содержимое сообщения с сервера.

### 🧠 Архитектурные инсайты (Архитектура медиаплеера и редактора)

#### Почему Flyweight?
В масштабных системах отрисовка тысяч иконок файлов (например, в проводнике) приводит к критическому перерасходу оперативной памяти (RAM). Паттерн **Flyweight (Легковес)** разделяет состояние объекта на:
* **Внутреннее (Разделяемое):** Хранится внутри объекта `FileIcon` (`file_type`). Оно неизменяемо.
* **Внешнее (Контекстное):** Передается извне в момент вызова метода (`x`, `y`).
Благодаря `IconFactory`, для миллиона файлов формата `.mp4` в памяти будет выделен физический объем только под **один** объект `FileIcon`.

#### Почему Facade?
Классы `VideoPlayer` и `AudioPlayer` представляют собой сложную низкоуровневую подсистему кодеков и декодеров. Без паттерна **Facade (Фасад)** клиентскому коду пришлось бы самостоятельно парсить строки, определять форматы и вызывать специфичные методы. Класс `MediaFacade` инкапсулирует эту сложность, предоставляя клиенту единую "ручку" — метод `play_media(file)`.

#### Почему Command?
Паттерн **Command (Команда)** превращает обычные запросы на изменение текста в самостоятельные объекты (`CutCommand`, `PasteCommand`). Это дает проекту три ключевых преимущества:
1. **Откладывание и очередь:** Команды можно передавать, логировать и ставить в очередь выполнения.
2. **Принцип Single Responsibility (SRP):** Класс `Editor` занимается только манипуляцией строками, а бизнес-логика триггеров (кнопки, горячие клавиши) изолирована в классах команд.
3. **Реализация Undo/Redo:** Стек `CommandHistory` запоминает состояние бэкапа (`_backup`) перед мутацией текста, позволяя откатывать систему к любой точке в прошлом без разрушения структуры данных.

1. **Связь «Оплата -> Проверка»:** Прецедент Покупателя `(Выбрать способ оплаты)` является обязательным входным условием для прецедента Сотрудника ПВЗ `(Проверка способа оплаты)`. Система автоматически блокирует выдачу, если транзакция не верифицирована.
2. **Связь «Идентификация -> Выдача»:** Действие Покупателя `(Получить штрих-код)` генерирует уникальный токен авторизации. Это является прямым триггером для действия Сотрудника ПВЗ `(Просканировать товар)`, переводя заказ в финальный статус "Выдано".
3. **Логистический триггер «Покупка -> Сборка»:** Факт успешного выполнения прецедента `(Купить)` мгновенно отправляет событие на склад, запуская автоматизированный процесс сборки заказа `(Собирать заказ)` силами сотрудников Департамента Логистики (`HumanDeport`).
4. **Маршрутизация доставки:** Выбор Покупателем конкретной опции `(Выбрать способ получения)` (например, курьерская доставка до двери или доставка в ПВЗ) напрямую влияет на алгоритмы Курьера `(Составлять маршрут)`, которые учитывают логистические стратегии отгрузки (FBO/FBS).
